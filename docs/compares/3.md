# Comparison 3 — pristine upstream `1c1a330` vs current HEAD `1fb8818`

Full re-measurement of the C99 → C++17 migration, run fresh end-to-end: every
value in [compares/2.md](2.md) re-derived independently, 11 commits later
(`4ed5d6a..1fb8818`), plus the one check 2.md's own session couldn't do yet
— confirming the `crankshaft`/`chi1` fix it found actually holds under the
same tool that found it. See [3-protocol.md](3-protocol.md) for the exact
commands behind every number below; it is written as a standalone tutorial,
not just a log, so this whole exercise can be repeated the same way again.

Measured 2026-08-30, same machine as comparison 2: gcc 13.3.0 / clang 18.1.3
/ Ubuntu 24.04 / x86-64, Intel i7-12650H (16 threads), single machine, all
binaries `-O3 -DNDEBUG`.

## Headline: nothing moved that shouldn't have, and one thing moved that should have

**Every pristine number reproduced exactly, seed-for-seed, from an
independent fresh build.** Pristine is a fixed, unchanging commit, so this
isn't surprising in principle — but it's worth stating plainly that it held
in practice too: the crash-rate map (4/16, 2/16, 2/16, 1/16 survivors at
50k/150k/250k/2.5M steps), the seed-10 divergence threshold (flips between
20,000 and 25,000 steps, same two values on both sides of the flip), the NS
energy sequence, and the `cm`/ASan/MSan findings all came back identical to
[compares/2.md](2.md), digit for digit, from a build done from scratch in a
different worktree, weeks of migration work later.

**The 11 commits since comparison 2 changed nothing this comparison can
see** — by design. Those commits (`4ed5d6a..1fb8818`) are three small bug
fixes, one CI change, one new opt-in flag defaulted off, and a three-commit
container conversion (`Chain`/`Chaint`'s remaining raw-pointer members to
`std::vector`) that was validated internally, per-commit, against bit-level
docking diffs at the time it landed. This comparison is the first
*external*, whole-migration confirmation that none of that work perturbed
anything pristine can be compared against — fold, the 16-seed docking sweep,
NS, and checkpoint format are all exactly where comparison 2 left them.

**The one thing that *should* differ from comparison 2, does.** 2.md's own
session found a real MSan `use-of-uninitialized-value` in `crankshaft()`
(`chi1`, uncopied by `transmutate`/`transmove`/`transopt`) on current HEAD —
present in that session's build because the fix (`5dd2a23`) hadn't landed
yet. This session's MSan docking reproduction, same seed, same options, same
step count, against a *fresh* current-HEAD MSan build: the `crankshaft`
report is gone. Only the two known `fopen`-adjacent false positives remain
(`mark_aa_from_file`, `biasmap_initialise`), matching what pristine itself
would show if pristine's version of the bug — which pristine still has,
frozen, forever — were fixed too. This is the fix being verified by the same
independent tool that found it, not just re-reading the commit message.

**A characterization refinement, not a new bug.** 2.md described pristine's
`bfactor` defect (mismatched-residue-count multi-model input) as something
that "didn't visibly crash on the plain build" and needed ASan to surface.
This session's plain, non-ASan run of the identical binary on the identical
fixture **hung** instead (`timeout 10` killed it, rc=124). Both symptoms are
consistent with the same underlying heap-buffer-overflow (confirmed again
under ASan below, same location as before); undefined behavior has no
required manifestation, and this is a small, concrete demonstration of that
— the "no visible symptom" framing from comparison 2 was true of that
session, not a property of the bug.

within ~0.5% either way; this run shows current ~5% ahead of pristine). Not

of which touch the fold hot path's allocation pattern in a way expected to
change per-step cost. Recorded as observed, not as a claimed improvement.

## Tools/ — real defects in pristine, all still present

- **`bfactor`**, multi-model input with mismatched residue counts: this
  session's plain run **hangs** (`rc=124` under a 10 s timeout) rather than
  completing silently-wrong as comparison 2's session observed — see the
  headline for why that's not a contradiction. ASan confirms the same
  underlying defect at the same location as before:
  `heap-buffer-overflow`, `READ of size 8`, `vector.c:37` in `subtract`,
  called from `bfactor.c:71` `update`. Current HEAD rejects the input with
  `"all models must have the same number of residues"` before touching the
  array.
- **`ramachandran`/`rama`**: pristine hangs indefinitely on
  `peptide12.pdb` (killed at a 5 s timeout); current HEAD completes
  normally. Matches the documented `goto`/uninitialized-`n1[1]`/`n1[2]` fix
  (`e072c1b`).
- **`cdlearn`**, long list-file token: pristine `SIGABRT`s
  (`rc=134`) with glibc's `*** buffer overflow detected ***`; current HEAD
  reports `"PDB base name from list file is too long"` and exits `rc=1`.
- **`cdlearn`**, baseline: run from a directory with `ramaprob.data`
  present, both binaries reach `"No list file given (-L option)"` (`rc=1`)
  — but only current HEAD prints `"ramaprob initialise success"` first,
  confirming it now initializes `ramaprob`/`alaprob`/`glyprob` unconditionally
  at startup where pristine still never does (a latent segfault on any real
  CD-learning run, not exercised by this smoke-level invocation).

## MemorySanitizer — the fix confirmed, independently, by the tool that found it

**Fold, current HEAD, `MSAN_OPTIONS=halt_on_error=0:abort_on_error=0:exitcode=0`:**
completes (`rc=0`) with exactly 1 warning — `biasmap_initialise`,
`energy.cpp:222`, the documented glibc-`fopen`-interceptor false positive
(same one `.github/workflows/ci.yml`'s `msan` job's comment describes).

**Docking, seed 10, redocking options, 25,000 steps:**

| binary | warnings | `crankshaft` report? |
|---|---|---|
| pristine | 1 | **yes** — `metropolis.c:732`, `use-of-uninitialized-value` |
| current HEAD | 2 (`mark_aa_from_file` `peptide.cpp:1996`, `biasmap_initialise` `energy.cpp:222`) | **no** |

Pristine's report is frozen at the same source line comparison 2 found it
at — it always will be, since pristine never changes. Current HEAD's two
remaining reports are the same class of `fopen`-interceptor false positive
as the fold run, at the same two locations this codebase's own CI/MIGRATION.md
documentation already names. The absence of a third report matching
`crankshaft` is the actual finding: `5dd2a23`
(`fix: transmutate/transmove/transopt never copied chi1/chi2, corrupting
docking`) closed the gap MSan opened in comparison 2, and this is that fix
being checked by the same independent tool, not by re-reading the diff.

## Conclusion

1. **Every previously-established fact reproduced exactly** — fold, the
   16-seed docking sweep, the crash-rate map (down to the same per-budget
   survivor counts), the seed-10 divergence threshold, NS, checkpoint
   format, and every tools/ finding. Three independent measurement sessions
   (compares/1.md's era, compares/2.md, this one) now agree on every shared
   number, from three separately-built binary pairs.
2. **The 11 commits since compares/2.md are externally invisible to this
   comparison, as intended.** Three bug fixes, a CI change, an opt-in flag
   defaulted off, and a three-commit container conversion validated
   per-commit at the time — none of it was expected to move a single number
   here, and none of it did.
3. **One thing did change, and it's the right one**: the `crankshaft`/`chi1`
   MSan finding compares/2.md surfaced on current HEAD is gone, confirmed
   independently by the same tool. Pristine's own copy of the bug is frozen
   forever, exactly where it was.
4. **A methodological note for whoever runs this next**: undefined behavior
   is still undefined behavior on the fourth measurement. `bfactor`'s
   symptom changed (silent corruption → a hang) between two sessions on
   ostensibly the same binary and input; confirm real findings under a
   sanitizer, not by trusting a plain-build symptom to repeat.
