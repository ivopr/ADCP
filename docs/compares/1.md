# Comparison 1 — pristine upstream `1c1a330` vs `f838cda`

Does the C99 → C++17 migration change what ADCP computes?

Measured 2026-08-29 on gcc 13.3.0 / glibc / x86-64. Baseline is `1c1a330`
("added license stuff", 2025-10-28) — the last upstream commit, before any of
this work. See [MIGRATION.md](../../MIGRATION.md) for the migration itself.

**How the baseline was built.** `git worktree add <tmp> 1c1a330`, then
`cc -std=c99 -O3 -DNDEBUG -fcommon <15 sources> -lm`. Two things are not optional:

- `-fcommon`. gcc ≥ 10 defaults to `-fno-common`, and upstream's headers carry tentative
  definitions (`spacing`, `NX`/`NY`/`NZ`, `centerX/Y/Z`, `gridmapvalues`, `transPtsCount`,
  `Xpts`/`Ypts`/`Zpts`, `ramaprob`) that do not link without it. HEAD links clean at
  `-fno-common`, which is `ADCP_LEGACY_COMMON=OFF`'s whole point.
- `-O3 -DNDEBUG`, to match `build-dock`'s `CMAKE_BUILD_TYPE=Release`. Rebuilding the
  baseline at its native `-O2` gives the same fold md5, so the optimizer level is not a
  variable here — but leaving it unmatched would have made it one.

CLI compatibility was verified before trusting any number: `adcp -h` is byte-identical
between the two binaries (modulo `argv[0]`), so every flag the 2026 test scripts pass
means the same thing to the 2025 binary. The scripts take the binary as `$1`, so the
baseline needed no test code of its own.

**Change 1 — nested sampling, deliberate.** `35fb3fb`, the fix for NS seeding new points
from the point being discarded. The before/after sequences reproduce the ones recorded
under "A real nested-sampling bug" in [MIGRATION.md](../../MIGRATION.md) exactly, which
also confirms that document's "before" numbers were taken against genuinely unmodified
code. The checkpoint restart differs for the same reason and no other: the file format is
unchanged, and HEAD reads a checkpoint the 2025 binary wrote.

**A second change was found, diagnosed and fixed.** Docking diverged from pristine past
200,000 steps until the `sqrt` precision defect below was corrected; with that fix in
place all 16 seeds match pristine bit-for-bit at full 2.5M-step length. An earlier
revision of this document claimed docking was identical on the strength of 10,000-step
runs alone — a budget below every swap threshold in `simulate()`, which never exercised
the diverging code. That is how the defect stayed hidden.

Folding, the grid energy path and the checkpoint format are bit-identical across the whole
C99 → C++17 migration. That includes `efa13ff`, whose "resolve all compiler warnings"
headline touched 41 lines of `energy.c`/`peptide.c`/`metropolis.c` and could plausibly have
moved numbers. It did not.

## Getting a full-length docking baseline out of a binary that segfaults

The pristine binary cannot run the 2.5M-step protocol — that is the `swapChains` overflow,
below. It can be made to complete **without touching its source**, by building it with
AddressSanitizer and letting it continue past the error:

```sh
cc -std=c99 -O3 -DNDEBUG -fcommon -fsanitize=address -fsanitize-recover=address -g ...
ASAN_OPTIONS=halt_on_error=0:detect_leaks=0:log_path=<dir>/asan
```

ASan places a redzone after the array, so the one-past write lands in memory nothing else
uses. The point is not that it survives — it is that ASan then *proves* what was touched.
Per run, across all 16 seeds, exactly two pre-existing defects and nothing else:

| ASan report | site | fixed later by |
|---|---|---|
| `dynamic-stack-buffer-overflow` ×5 | `swapChains[10]`: write at `main.c:237`, reads at `:258`, `:368`, `:383`, `:535` | `7e2192d` |
| `stack-buffer-overflow` ×1 | `sscanf` in `model_param_read`, `params.c:1121` | `1e82869` |

All five `swapChains` accesses report the **same 8-byte address** — one redzone slot,
written once at init and read back unchanged. No live data is touched.

Three controls, because a baseline nobody can trust is worse than none:

- **ASan does not move the numbers.** Plain pristine vs ASan pristine, 16 seeds ×
  10,000 steps: 0/16 differ, in targetE *and* ATOM md5. HEAD under ASan vs HEAD plain at
  250,000 steps: identical ATOM md5. At 2,500,000 steps: both -20.6324.
- **The result does not depend on uninitialized memory.** Re-running with
  `malloc_fill_byte` at 0, 17, 190 and 255 gives byte-identical output every time, so the
  `Chain` members pristine leaves uninitialized (later closed by `new Chain{}`) are not
  feeding the answer.
- **It is reproducible.** Repeated runs at fixed settings agree exactly.

## The docking path was not bit-identical — a `sqrt` precision defect (fixed)

Pristine and HEAD agree exactly through 150,000 steps and diverge at **200,000** —
`swapMutateSteps`. Seed 4242, same options as `run_dock_test.sh`:

| steps | pristine targetE | HEAD targetE | ATOM records |
|---|---|---|---|
| 10,000 | -10.0602 | -10.0602 | same |
| 50,000 | -10.8686 | -10.8686 | same |
| 150,000 | -13.6251 | -13.6251 | same |
| 200,000 | -13.6251 | -13.6251 | **diverged** |
| 250,000 | -13.6251 | -15.8192 | diverged |

`git bisect` over `7e2192d..master`, probing seed 4242 at 250,000 steps, gives a single
first-bad commit:

```
5660a33  build: convert energy.c, probe.c, metropolis.c, flex.c,
         checkpoint_io.c and nested.c to C++
```

A Phase 1 rename step, which was supposed to be behaviour-neutral. `energy.cpp` alone
carries 195 changed lines in it. This is the **same commit** [MIGRATION.md](../../MIGRATION.md)
already names for the intermittent fold hang, and whose section "MECHANISM RESOLVED — `tc`
was a red herring; the real bug is still latent" concludes the underlying defect is still
in the tree. That section could only observe the bug as a ~23% intermittent hang. This is a
second, **deterministic** symptom of something introduced by the same commit — a far better
handle for finding it.

Neither endpoint failed the 2.5 Å criterion (0.66 Å pristine vs 0.72 Å for the defective
build), so this never showed up as a quality regression — which is exactly why it needed
a bit-level comparison to find.

### Root cause: `sqrt` on a `float` argument means something different in C++

`normalizedVector` and the two vector normalisations inside `scoreSideChain`/
`scoreSideChainNoClash` all have this shape, unchanged by the migration:

```c
float v[3];
n = 1. / sqrt(v[0] * v[0] + v[1] * v[1] + v[2] * v[2]);
```

The sum is a `float`. In **C**, `sqrt` is `double sqrt(double)` — the only one there is —
so the value widens to `double`, the square root is taken in double precision, and the
reciprocal is a double divide. In **C++**, `<math.h>` also brings in the C++ overload set,
and the argument binds to **`float sqrt(float)`**. The square root is now computed and
rounded in single precision *before* the divide.

One extra rounding, at `2^-23` ≈ 1.2e-7 relative — which is exactly the discrepancy
measured. Instrumenting both trees at `-O0` shows `v1`/`v2`/`v3` diverging in their last
float digit on the very first call, before `tc` or `coords` are read at all, which is why
neither the `View3` parameter change nor the `tc` storage change turned out to be the
culprit — both were tested and reverted independently without effect.

Confirmed end to end: `5660a33` with the five affected `sqrt` calls forced back to double —
and **nothing else changed** — reproduces the pristine `-13.6251` exactly.

```c
n = 1. / sqrt((double)(v[0] * v[0] + v[1] * v[1] + v[2] * v[2]));
```

The five sites are [src/energy.cpp](../../src/energy.cpp) lines 1485, 1556, 1559, 1719 and
1722. A survey of `sqrt`/`fabs`/`pow`/`exp`/`log`/`sin`/`cos`/`acos`/`atan2` across `src/`
finds **no other call taking a `float` argument**, so the blast radius is exactly these
five lines.

**Which lineage is right?** The C one. Nothing chose single precision here — it is an
artefact of the language change, and it made the normalisation strictly less accurate
than what produced ADCP's published results.

**Fixed.** The five sites now cast to `double`, with a comment saying why, so the casts
are not "simplified" away later. After the fix: seed 4242 at 250k gives `-13.6251`; all
16 seeds at 10,000 steps and all 16 at 2,500,000 steps match pristine in both targetE and
ATOM md5; the full redock returns to targetE -28.5508 / RMSD 0.66 Å. Folding, NS and
checkpointing are untouched. 15/15 ctest, 15/15 under ASan+UBSan, 3/3 docking and
validation.

This is also a generic C→C++ conversion hazard worth carrying forward: any math function
applied to a `float` expression silently drops to single precision in C++, and no warning
fires by default. `-Wdouble-promotion` does not catch it — it warns about the opposite
direction.

## The docking crash threshold is much lower than 200,000 steps

`7e2192d` reports the [main.cpp](../../src/main.cpp) `swapChains` overflow as gated behind `swapMutateSteps = 200000`.
That holds for [run_dock_test.sh](../../tests/run_dock_test.sh)'s option set. It does **not** hold for the redocking
option set (`external=5,con,1.0,1.0,Opt=1,0.25,0.75,0.0`), where the pristine binary
segfaults from ~75,000 steps on seed 1, and 12 of 16 seeds already crash at 50,000:

| steps, redock OPTS | pristine runs completing, seeds 1-16 |
|---|---|
| 10,000 | 16/16 |
| 25,000 | 7/16 |
| 50,000 | 4/16 |
| 150,000 | 2/16 |
| 250,000 ([run_dock_test.sh](../../tests/run_dock_test.sh)) | crashes, rc 139 |

So 10,000 steps is the largest budget on which the *plain* pristine build can dock at all
across these seeds — the ASan build above lifts that restriction entirely. The practical
reading: the bug's reach was wider than the original bisect suggested.

## Reproducing this

The three functional scripts and [run_redock_validation.sh](../../tests/run_redock_validation.sh) all take the binary as `$1`,
so the whole comparison is: build the baseline as above, then run each script twice —
once with the baseline binary, once with `build-dock/src/adcp` — pointing them at
`data/ramaprob.data`, `tests/data/output.pdb` and `build-dock/tests/target/stage`. For the
docking side use `run_redock_validation.sh <bin> <stage> <wd> 16 10000 99`; the 99 Å
threshold makes it report rather than fail, since 10,000 steps is a determinism probe,
not a docking run.

For the full-length baseline, build the pristine tree with the ASan flags above, export
`ASAN_OPTIONS`, and run `run_redock_validation.sh <asan_bin> <stage> <wd> 16 2500000 2.5`
— 3 m 24 s on 14 cores. To re-derive the divergence, probe seed 4242 at 250,000 steps and
compare against `-13.6251`; that is an ~8 s check, which is what made the bisect over
`7e2192d..master` cheap.
