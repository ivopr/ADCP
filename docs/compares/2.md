# Comparison 2 — pristine upstream `1c1a330` vs current HEAD `4ed5d6a`

Full re-measurement of the C99 → C++17 migration: every value in
[compares/1.md](1.md) re-derived independently against the current tip, plus
timing, memory, binary size, compile time, and a tools/ correctness sweep that
document did not cover. See [2-protocol.md](2-protocol.md) for the exact
commands behind every number below.

Measured 2026-08-29 on gcc 13.3.0 / Ubuntu 24.04 / x86-64, Intel i7-12650H (16
threads), single machine, all binaries `-O3 -DNDEBUG`.

## Headline: one finding not previously documented

**Pristine's own docking output, for seeds that don't crash, is built on
undefined behavior — "bit-identical to pristine" is not the stable ground
truth it was assumed to be.** Seed 10 of the standard 16-seed redocking sweep
diverges from pristine between 20,000 and 25,000 steps under the redocking
option set — thousands of steps below the previously-documented 200,000-step
`swapMutateSteps` threshold, and with the `sqrt`-precision defect already
fixed on both sides. Isolating the change (patching *only* the pristine C
source's `swapChains` array from `[swapLength]` to `[swapLength+1]`, with
nothing else touched, still 100% pristine C) reproduces current HEAD's value
exactly. The array is never indexed at `[swapLength]` below step 200,000, so
resizing it should be a no-op — it isn't, which means some other local in the
same stack frame is read uninitialized, and its garbage value depends on
frame layout. See "The new finding" below for the full derivation. This is a
**pre-migration** defect, present in true pristine upstream and merely
*inherited* — not introduced — by `7e2192d`, the very fix that stopped the
crashes. It was invisible until now because every prior comparison used
budgets short enough to avoid it, or measured only completion/RMSD rather
than bit-level trajectories at intermediate step counts.

**Confirmed directly with MemorySanitizer, on both binaries.** Beyond the
`swapChains`-adjacent story above, MSan independently catches a second,
more central use-of-uninitialized-value defect — an unset `chi1` dihedral
angle read inside `crankshaft()`, the core Monte Carlo move function, on
the exact same relative line in both pristine (`metropolis.c:732`) and
current HEAD (`metropolis.cpp:727`), via an identical call chain
(`crankshaft → move → simulate → main`). It is byte-identical in both
binaries — not introduced or fixed by the migration, just carried through
it unchanged. See "Pinning the exact uninitialized variable" below for the
full derivation, including how to get MSan to run past the other known
false-positive noise (plain glibc's `fopen()` interceptor).

pristine's crash rate, which is the more important story anyway (see

## The new finding, in full

Reproduction, seed 10, redocking option set
(`Bias=NULL,external=5,con,1.0,1.0,Opt=1,0.25,0.75,0.0`):

| steps | pristine targetE | current targetE |
|---|---|---|
| 10,000 | -11.9092 | -11.9092 |
| 15,000 | -11.9092 | -11.9092 |
| 20,000 | -11.9092 | -11.9092 |
| 25,000 | **-15.3654** | **-11.9092** |
| 50,000 | -15.3654 | -11.9092 |
| 150,000 | -26.9252 | -19.1854 |
| 250,000 | -27.2513 | -23.889 |
| 500,000+ | -28.2719 | -23.889 → -24.1148 |

`git bisect` narrowed this to a single commit: `7e2192d`, the fix for the
`swapChains` stack-buffer overflow that crashes production docking (already
documented in MIGRATION.md and compares/1.md as *the* crash fix — but not
previously checked for effects on runs that don't crash). Every commit
between `1c1a330` and `7e2192d` (`ae2f242`, `0375337`, `fb04806`, `25caff5`,
`1c74e47`, `99b55aa`, `69a01f6`, `28ef037`) reproduces pristine's `-15.3654`
exactly; `7e2192d` is the first to give `-11.9092`.

`7e2192d`'s diff touches three things: the `swapChains` array size, and two
`NULL`-check additions in `energy.c` for missing grid/transpoints files —
neither guard fires in this reproduction (all files are present). Isolating
the array-size change alone — patched into an otherwise-untouched copy of
pristine's `main.c`, nothing else in the tree modified, still compiled as
plain C99 — reproduces `-11.9092` exactly:

```diff
- Chain* swapChains[swapLength];
+ Chain* swapChains[swapLength + 1];
```

`swapChains[swapLength]` (the new slot) is read only when
`swapMutateSteps` (200,000) is reached — far above where the divergence
appears (20,000–25,000 steps) — so the fix's own commit message reasoning
("shorter runs never reached the corrupted slot") is correct about *that*
slot, but incomplete: changing the array's *size* shifts the stack layout
of `simulate()`'s frame, and something else in that frame is evidently read
before it is written. The array-size change is a proxy for "reshuffle the
stack" — it isn't touching live data, it's exposing a pre-existing
uninitialized-read bug whose garbage value depends on frame layout.

**This means neither `-15.3654` (pristine) nor `-11.9092` (current) is a
"correct" reference value for seed 10 past ~20,000 steps under this option
set — both are outputs of undefined behavior, just at different points in
the same UB's exposure.** The value is reproducible per-binary (same
compiler, same flags, same stack layout every run), which is why the
existing determinism tests all pass — determinism and correctness are
different properties, and this defect breaks only the second one.

**Update: pinned exactly, on both binaries, via MSan.** The blocker
described above (plain glibc `fopen()` producing a confirmed false positive)
turned out to be avoidable without an instrumented libc: `MSAN_OPTIONS`
needs `abort_on_error=0` in addition to `halt_on_error=0` — the latter alone
still terminates the process, since MSan's own `-help=1` dump says
continue-after-report dedup is "(asan only)". With both set, the report
narrows the fopen noise (`biasmap_initialise`, `mark_aa_from_file`) down to
a confirmed sanitizer artifact — MSan's own diagnostic literally says
`Uninitialized bytes in fopen at offset 4 inside [...]`, i.e. the complaint
is about MSan's `fopen` interceptor's internal state, not about ADCP —
exactly the class of false positive this repo's CI notes already documented
for `biasmap_initialise()`.

Past that noise, both binaries hit the same real warning, at the same
logical statement, reached through an identical call chain:

| | pristine | current HEAD |
|---|---|---|
| site | `crankshaft`, `metropolis.c:732` | `crankshaft`, `metropolis.cpp:727` |
| call chain | `crankshaft → move → simulate → main` | identical |
| statement | `chain->aa[i].chi1 != DBL_MAX` | same, unchanged by the migration |

The read is `chain->aa[i].chi1` — a side-chain dihedral angle — guarded by
`chain->aa[i].id != 'G' && chain->aa[i].id != 'A'` (glycine and alanine have
no `chi1`, so the check is meant to skip them). For at least one non-G/A
residue on this trajectory, `chi1` is read before anything ever assigns it.
**This bug is byte-identical in both binaries** — not introduced by the
migration, not fixed by it, inherited unchanged from pristine C straight
through the C++ conversion. It predates `7e2192d` and is independent of the
`swapChains` story above; the two are separate defects that happen to sit
in neighboring functions (`crankshaft`/`move` vs. `simulate`'s stack frame).

This closed the open question from the first pass at this document: **yes,
current HEAD had the same use-of-uninitialized-value defect pristine has.**

**Update (fixed).** The root cause turned out to be one level upstream of
`crankshaft`/`move`: `crankshaft()` and `crankshaftcyclic()` are actually
self-healing (both always overwrite `chaint->aat[i].chi1`/`.chi2` themselves
before reading them back) — they're just where MSan happens to catch the
symptom. The real writers were `transmutate()`, `transmove()`, `transopt()`
(`src/metropolis.cpp`, all docking-only), each of which copies a subset of
`AA` fields into a scratch buffer, omits `chi1`/`chi2`, and later commits the
move with a full struct assignment that silently overwrites the previously
valid dihedral angles with `aat_init()`'s uninitialized scratch memory. Fixed
by adding the two omitted fields to each copy loop, plus `aat_init()` itself
as defense in depth — five lines total, no shared-helper refactor (matches
this repo's established convention of narrow, single-purpose fixes). Full
derivation and verification recorded in
[MIGRATION.md](../../MIGRATION.md#fixed--chi1chi2-uninitialized-value-bug-msan-pre-existing-since-pristine).

Current HEAD no longer has this defect. **Pristine still does** — it is
frozen upstream and was not touched. This is a third deliberate,
documented divergence from pristine, alongside the NS point-seeding fix and
the `sqrt`-precision fix, for docking budgets below the point where
`crankshaft`'s own 1-in-4 resampling naturally self-corrects the corruption
(measured: the bug is visible at the 25,000-step budget this section
discovered it at, but the fix left both of this repo's own validated
benchmarks — the 250,000-step `dock_3q47_smoke` and the full 2,500,000-step
16-seed `val_3q47_redock` — bit-for-bit unchanged, since real searches run
long enough for the self-correction to complete before it matters).

## Tools/ — real, ASan-confirmed defects in pristine

`cm` is byte-identical on `peptide12.pdb`; the other three show real defects
current HEAD closes:

- **`bfactor`**, multi-model input with mismatched residue counts: pristine
  reads both models with no validation; under ASan this is a confirmed
  **heap-buffer-overflow** (`vector.c:37` `subtract`, reading 8 bytes past a
  3016-byte allocation). Current HEAD detects the mismatch and reports
  `"all models must have the same number of residues"` before touching the
  array. Non-ASan pristine doesn't crash on this input — it silently reads
  adjacent heap memory, i.e. exactly the "no visible symptom, still wrong"
  failure mode this whole comparison keeps surfacing.
- **`ramachandran`**, `peptide12.pdb` on stdin: pristine hangs indefinitely
  (killed at the 5 s timeout used here); current HEAD completes normally.
  Matches the documented `goto`/uninitialized-`n1[1]`/`n1[2]` fix
  (`e072c1b`).
- **`cdlearn`**, a list-file token longer than the 1024-byte buffer:
  pristine `SIGABRT`s with glibc's `*** buffer overflow detected ***`
  (`_FORTIFY_SOURCE` catching a real stack smash) — not a graceful failure,
  a crash. Current HEAD reports `"PDB base name from list file is too
  long"` and exits cleanly.
- **`cdlearn`**, baseline invocation with no arguments: pristine never
  prints anything about `ramaprob` — it never calls
  `ramaprob_initialise()`, so `ramaprob`/`alaprob`/`glyprob` stay `NULL`.
  This doesn't crash on the smoke-test path because that path never reaches
  `ramabias()`, but it is a **latent segfault** on any real CD-learning run.
  Current HEAD calls the initializer and prints
  `"ramaprob initialise success"` before doing anything else.

## Conclusion

The migration's own correctness claims hold up under independent
re-measurement, with two caveats this document adds:

1. **Confirmed, unchanged from compares/1.md:** folding, the grid-energy
   path (within the domain both binaries can actually complete), the
   checkpoint file format, and CLI compatibility are exactly as documented.
   Docking is bit-identical at every budget where pristine survives to
   compare against.
2. **New, and more consequential than a "still matches" result:** past a
   seed- and option-set-dependent step count — as low as 20,000–25,000 steps
   for at least one of the 16 standard seeds — pristine's own output is not
   a valid reference, because it depends on undefined behavior predating the
   C++ migration by 12 commits. "Does the migration match pristine"
   presupposes pristine has one true answer to match; past this threshold,
   for this seed, it does not. Framing the remaining gap as "current HEAD
   differs from pristine" would be the wrong lesson — the right one is that
   the pristine baseline itself needs the same UB audit `7e2192d`,
   `1e82869`, and the ASan/UBSan CI leg already gave everything downstream
   of it.
3. **Performance:** no measurable per-step throughput regression (within
   1% on the one apples-to-apples budget both binaries can run). Memory
   footprint is up ~50% on the small folding workload and single-threaded
   compile time is up ~73% — both expected costs of `std::string`/
   `std::vector` and C++17 template instantiation, and both small in
   absolute terms for a CLI tool invoked once per docking run.
4. **The pristine binary cannot run its own documented production protocol**
   (`-N 50 -n 2500000`, per `7e2192d`'s commit message) without crashing on
   15 of 16 standard seeds. Current HEAD runs it in 101.85 s and reproduces
   the published 0.66 Å redocking result. This, not the bit-level
   comparison, is the practical bottom line: pristine upstream is not
   usable for real docking runs; current HEAD is.
